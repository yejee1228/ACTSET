# 기술 검증 PoC 계획 (Stage 8)

> **서비스명: ACTSET** / 개발기획(Stage 9~)에 앞서 수행하는 선행 검증

## 목적

Stage 5에서 채택한 **레이어 분리 구조**가 실제로 동작하는지 확인한다. 이 검증이 끝나야 기술 스택·DB 스키마·API 명세를 확정할 수 있다. 반대로 여기서 실패하면 설계 상당 부분을 되돌려야 하므로, 문서를 더 쓰기 전에 먼저 돌려본다.

PoC는 제품을 만드는 작업이 아니다. **스크립트 몇 개로 결과 이미지를 뽑아 눈으로 확인하는 것**이 전부이며, 여기서 만든 코드는 버려도 된다.

## 검증 질문과 성공 기준

### Q1. 생성 이미지에 원치 않는 글자가 섞이지 않는가 (재정의)

**당초 질문은 "한글 공연명을 정확히 렌더링하는가"였으나, 모든 텍스트를 별도 레이어로 얹기로 확정하면서 질문 자체가 바뀌었다.** 이제 생성 모델의 한글 실력은 중요하지 않다. 오히려 **생성 이미지에 글자가 하나도 없어야 한다.**

생성 모델은 요청하지 않아도 포스터풍 이미지를 만들 때 글자 비슷한 형태를 배경에 그려 넣는 경향이 있다. 우리가 그 위에 실제 텍스트를 얹으므로, 배경의 가짜 글자는 그대로 노이즈가 된다.

- **방법**: 네거티브 프롬프트(`no text, no letters, no typography`)를 넣은 경우와 넣지 않은 경우를 각 10건 생성해 비교
- **성공 기준**: 네거티브 프롬프트 적용 시 글자 형태가 나타나지 않은 비율 80% 이상
- **실패 시**: 인페인팅으로 제거하는 후처리 단계를 파이프라인에 추가한다(원가 상승)
- **함께 확인**: Default($0.06)와 Quality($0.10)의 배경 품질 차이 — 후보는 Default, 확정본은 Quality로 나누는 전략의 타당성 판단

**이 재정의로 PoC의 최대 불확실성이 사라졌다.** 아키텍처가 생성 모델의 한국어 지원 여부에 걸리지 않는다.

### Q2. 정보를 얹을 여백이 확보되는가

- **방법**: "하단 1/3은 단순한 배경" 등 여백 지시를 넣은 프롬프트와 넣지 않은 프롬프트를 비교 생성
- **성공 기준**: 여백 지시가 반영된 결과가 과반 이상 나오고, 그 영역에 텍스트 레이어를 얹었을 때 가독성이 확보됨
- **실패 시**: 정보 영역에 반투명 박스를 까는 방식 등 대안을 검토

### Q3. 텍스트 레이어 합성이 의도대로 동작하는가

- **방법**: 생성된 배경 위에 날짜·장소·출연진·주최 정보를 폰트로 렌더링해 합성. 정보를 바꿔 재합성했을 때 배경은 그대로이고 텍스트만 바뀌는지 확인
- **성공 기준**: 정보 수정 → 재합성이 이미지 생성 API 호출 없이 수초 내에 완료됨
- **의의**: 이것이 성립해야 `auto_sync_text`(포스터 자동반영)와 무과금 정책이 유지된다

### Q4. 규격 변환이 성립하는가

- **방법**: 세로 포스터 1장을 정사각형(SNS 1:1)과 가로 긴 규격(현수막)으로 변환. **분해된 레이어 스택을 재배치**하는 방식으로 검증한다 — 배경판만 확장하고 피사체는 잘라내지 않고 이동시킨다
- **성공 기준**: 주요 피사체가 잘리지 않고, 정보가 규격에 맞게 재배치되어 읽을 수 있는 결과가 나옴
- **주의**: 통짜 이미지를 크롭하는 방식은 1차 검증에서 이미 실패했다(아래 결과 참조). 레이어 분리를 전제로 다시 검증한다. 관건은 **배경판만 확장하는 아웃페인팅**이며, 완성 포스터를 확장하는 것보다 대상이 단순해 성공 가능성이 높다

### Q5. 인쇄 해상도를 확보할 수 있는가

기존 기획에서 다루지 않았던 항목이다.

- **배경**: 생성 API 출력은 보통 1024~2048px인데, A3 포스터 300dpi는 3508×4961px다. 그대로는 인쇄 품질에 미달한다
- **방법**: 생성 이미지를 업스케일한 뒤 텍스트 레이어를 인쇄 해상도로 재렌더링해 합성하고, 실물 크기로 출력해 확인
- **성공 기준**: 인쇄물에서 텍스트가 선명하고 배경에 뭉개짐이 두드러지지 않음
- **참고**: 텍스트 레이어는 원본 해상도로 다시 그리므로 텍스트는 선명하게 나온다. 관건은 배경 업스케일 품질이다

### Q6. 생성 이미지가 쓸 만한 레이어로 분해되는가 (신규)

레이어 스택 구조의 전제다. 여기가 무너지면 규격 변환 전략 전체를 다시 짜야 한다.

- **방법**: 생성된 포스터 비주얼 10건을 Qwen-Image-Layered로 분해
- **성공 기준**
  - 배경판·피사체·장식이 의미 있는 단위로 나뉜다(피사체가 조각나거나 배경에 눌어붙지 않는다)
  - 피사체를 제거한 배경판에 큰 구멍이 남지 않는다
  - 마스크 경계가 깨끗해 재배치 시 티가 나지 않는다
- **실패 시**: SAM2로 피사체만 분리하고 나머지는 통짜로 두는 절충안, 또는 규격별 배경 별도 생성으로 후퇴
- **함께 확인**: 분해 1회 비용과 소요 시간, 저장 용량 증가분

### Q7. AI 타이포그래피를 별도 레이어로 뽑을 수 있는가 (신규, 선택)

타이틀 모드 B의 성립 여부다. 기본 모드(폰트 렌더링)가 이미 검증되었으므로 **실패해도 서비스에 지장은 없다.**

- **방법**: Qwen-Image-3.0으로 한글 공연명 타이포그래피를 생성하고, 투명 배경으로 분리 가능한지 확인
- **성공 기준**: 한글 오타 없음, 배경 분리 후 경계가 깨끗함
- **주의**: 문자열을 따옴표로 감싸고 프롬프트 자동 확장을 끈다. 켜져 있으면 모델이 문구를 바꾼다

## 테스트 케이스

장르에 따라 정보 구성과 배치 관습이 다르므로 성격이 다른 2개 장르로 검증한다.

| 케이스 | 장르 | 특징 |
|---|---|---|
| A | 클래식 | 출연진 경력 표기, 정보량 많음, 정제된 톤 |

# 1차 검증 결과 (텍스트 렌더링 엔진 실제 구동)

이미지 생성 API 없이도 확인 가능한 Q3·Q4·Q5를 먼저 구현해 실행하였다. 코드는 `poc/engine.py`, `poc/run.py`, 결과 이미지는 `poc/out/`에 있다.

## Q3. 정보 수정 재합성 — **통과**

- 날짜·장소를 바꿔 재합성한 결과, 비주얼 레이어는 픽셀 단위로 동일하고 텍스트만 교체됨
- 소요 **205ms**, 이미지 생성 API 호출 **0회**
- **의의**: Stage 6에서 "포스터 자동반영은 무과금"으로 정한 것이 기술적으로 성립함을 확인. `base_image_url` 재사용 구조가 유효하다

## Q4. 규격 변환 — **부분 통과 (중요한 한계 발견)**

| 규격 | 결과 | 비고 |
|---|---|---|
| SNS 1:1, SNS 스토리, X배너 | 통과 | 세로 계열은 크롭만으로 사용 가능한 결과가 나옴 |
| 홈페이지 배너(1920×600), 현수막(2048×256) | **실패** | 세로 원본을 가로로 크롭하면 키비주얼이 잘려 사라지고 밋밋한 띠만 남음 |

**결론**: 가로로 긴 규격은 크롭만으로 만들 수 없다. 배경 아웃페인팅(좌우 확장)이 필수이며, 그 품질이 확보되지 않으면 **규격별로 배경을 따로 생성하는 방식**을 택해야 한다. 이 판단은 이미지 생성 API 확보 후 재검증 대상이다.

**부수 확인**: 초기 실행에서는 일부 소규격이 영역을 초과해 Stage 5의 "필수문구 경고" 규칙이 발동했다. 다만 이는 줄간격을 지나치게 넓게 잡았던 탓이며, 간격을 조정한 뒤에는 전 규격이 영역 안에 들어갔다. 경고 규칙 자체는 필수문구가 여러 건일 때를 대비해 유지하되, **초과 상황이 일상적으로 발생한다고 단정할 근거는 아직 없다.**

**개선 필요**: 정보 생략 순서를 전 장르 공통으로 두었더니 SNS 1:1에서 출연진·가격까지 사라졌다. 클래식은 출연진이, 어린이공연은 가격이 더 중요할 수 있으므로 **장르별 생략 순서가 필요하다**는 점이 드러났다. 다만 무엇을 남길지는 학습 결과로 정해야 한다(Stage 5의 0-3 참고).

> **중요 — 이 PoC의 배치값은 디자인 결정이 아니다**
> `poc/engine.py`의 `RULES`(정보영역 위치, 글자 크기 비율, 생략 순서)는 엔진이 **동작하는지** 보기 위한 임시값이다. ACTSET의 레이아웃은 포스터 100건 → 10,000건 학습으로 도출되며, 현재는 그 근거가 없는 상태다. 이 값들을 기준으로 삼거나 문서에 확정값으로 옮겨 적어서는 안 된다.

## Q5. 인쇄 해상도 — **통과**

- A3 300dpi(3508×4961px)로 출력. 배경은 **2.8배 업스케일** 필요
- 텍스트 레이어를 300dpi로 재렌더링한 결과 텍스트가 100% 확대에서도 완전히 선명함
- **의의**: 레이어 분리 구조의 부수 이점이 확인됨. 통생성 방식이었다면 텍스트도 함께 뭉개졌을 것이다

## Q1·Q2 — 미검증

이미지 생성 API 키가 필요하다. 다만 **아키텍처 결정은 더 이상 여기에 걸려 있지 않다**(모든 텍스트를 별도 레이어로 확정). 배경 품질과 프롬프트 전략을 다듬는 검증으로 성격이 바뀌었다.

## 부산물 — 규격 치수 확보

검증 과정에서 규격별 실제 **치수**를 정리하였다(`poc/engine.py`의 `FORMATS`. 이후 예매처 3종이 추가되어 현재 13종). 치수는 매체가 정한 값이므로 학습과 무관하게 확정할 수 있어 Stage 12의 초안으로 쓸 수 있다. 반면 같은 파일의 `RULES`(배치 기준)는 위 경고대로 임시값이다.

## 추가 검증 — Java2D 이식 가능성

개발 인력이 모두 Java 개발자라는 조건이 확인되어, 텍스트 렌더러를 **Java2D로 이식해 동일 포스터를 렌더링**하였다(`poc-java/PosterRenderer.java`).

| 항목 | Python (Pillow) | Java (Java2D) |
|---|---|---|
| 한글 렌더링 | 정상 | 정상 (Noto Sans CJK KR을 TTC에서 직접 로드) |
| 텍스트 레이어 합성 | 86ms | 82ms |
| A3 300dpi 텍스트 | 선명 | 선명 |
| 결과물 | — | 육안 구분 불가 |

**결론**: 렌더링 엔진은 Java로 구현해도 무방하다. AI 모델들은 어차피 HTTP로 호출하므로, Python을 운영 코드베이스에 둘 이유가 없어졌다. Stage 9를 Java 단일 백엔드로 개정하였다.

## 추가 검증 — TITLE 레이어 효과

모든 텍스트를 이미지 위에 얹기로 확정하면서, **타이틀이 배경에 녹아든 디자인 없이도 성립하는지** 확인하였다(`poc-java/TitleLayerDemo.java`). 타이틀을 밝은 피사체 위에 겹치는 가장 불리한 조건으로 렌더링했다.

| 처리 | 결과 |
|---|---|
| 기본(흰색 채움) | 밝은 배경과 겹치는 구간에서 가독성이 떨어진다 |
| **외곽선 + 그림자** | 어떤 배경 위에서도 안정적으로 읽힌다. **기본값으로 권장** |
| 그라디언트 + 글로우 | 장식성이 높다. 장르·톤에 따라 선택 |

**결론**: 배경 밝기와 무관하게 타이틀 가독성을 확보할 수 있다. 외곽선·그림자를 기본으로 적용하고, 효과의 종류·강도는 학습으로 도출되는 장르별 값에 포함시킨다.

## 종합 판단

레이어 분리 구조는 **유효하다.** 정보 자동반영과 인쇄 품질이라는 두 축이 실제로 동작함을 확인하였다.

남은 위험은 **가로 규격 변환** 하나로 좁혀졌다. 이는 이미지 생성·아웃페인팅 API 품질에 달려 있으므로, API 확보 후 Q1·Q2와 함께 2차 검증한다.
