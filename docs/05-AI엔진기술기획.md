# AI 엔진 기술기획 (Stage 5)

## 목적

Stage 1~4에서 정의한 기능을 실제로 동작시키는 4개 엔진(Genre Rules, Format Rules, Recomposition Engine, 생성 파이프라인)의 내부 로직을 설계한다. 이 문서가 확정되어야 Stage 7(개발마일스톤)에서 실제 개발 티켓(어떤 모델을 어떤 순서로 호출할지)을 뽑을 수 있다.

## 0. 레이어 아키텍처 — 가장 중요한 설계 전제

ACTSET의 핵심 기능(정보 수정 자동반영, 규격 일괄변환, 객체 단위 편집, 인쇄용 출력)은 모두 **텍스트가 이미지 픽셀과 분리되어 있을 때만** 성립한다.

**모든 텍스트는 생성 이미지에 녹이지 않고, 완성된 이미지 위에 별도 레이어로 얹는다.** 공연명을 포함해 예외를 두지 않는다. 이전에 열어두었던 A안(공연명을 이미지에 포함해 생성)은 **폐기**한다.

### 레이어 스택 — 개수는 고정이 아니다

레이어를 4개로 못박지 않는다. **비주얼 레이어는 분해 결과에 따라 개수가 달라지고**, 텍스트·마크 레이어는 역할이 정해져 있다.

| 그룹 | 타입 | 개수 | 생성 주체 | 규격 변환 시 동작 |
|---|---|---|---|---|
| 비주얼 | `BACKDROP` 배경판 | 1 | 이미지 생성 API | **확장·크롭** — 아웃페인팅 대상은 여기뿐 |
| 비주얼 | `SUBJECT` 주요 피사체 | 0~n | 분해 결과 | 이동·스케일·좌우반전 |
| 비주얼 | `DECOR` 장식 요소 | 0~n | 분해 결과 | 이동·복제·생략 |
| 텍스트 | `TITLE` 타이틀 | 1 | 폰트 렌더링 또는 AI 타이포그래피 | **항상 유지**, 크기·위치만 조정 |
| 텍스트 | `INFO` 정보 | 1 | 폰트 렌더링 | 우선순위대로 생략·축약·재배치 |
| 사진 | `PHOTO` 업로드 사진 | 0~n | **고객 업로드 + 자체 합성** | 이동·스케일, 비율 유지. 액자형 배치 |
| 마크 | `MARK` 로고 | 0~n | 이미지 합성 | 비율 유지, 최소 크기 보장 |

렌더링은 BACKDROP → SUBJECT → DECOR → PHOTO → TITLE → INFO → MARK 순으로 쌓는다.

### 업로드 사진 처리 원칙 — 외부에 보내지 않는다

**고객이 업로드한 인물 사진(출연진 사진·공연 사진)은 어떤 외부 AI API에도 전송하지 않는다.** 생성 프롬프트의 입력으로도, 레이어 분해·세그멘테이션의 대상으로도 쓰지 않는다. 자체 엔진(Java2D)이 `PHOTO` 레이어로 직접 합성한다 — 텍스트 레이어와 같은 원리다.

이 원칙이 만드는 것:

- **국외이전 문제가 설계로 사라진다.** 얼굴이 담긴 개인정보가 해외 서버로 나가지 않으므로, 국외이전 고지·동의 부담이 사진에 대해서는 발생하지 않는다(Stage 15)
- **원본 화질이 유지된다.** 생성 모델을 거치지 않으므로 얼굴이 변형되거나 열화되지 않는다 — 출연진 사진에서 이것은 품질이 아니라 신뢰의 문제다
- **규격 변환이 자유롭다.** 사진은 독립 레이어이므로 규격마다 재배치·재스케일하면 되고, 재생성이 필요 없다

**MVP의 배치 방식은 액자형이다.** 사진을 사각·라운드·원형 마스크로 잘라 배치한다(클래식 포스터의 프로필 사진 관행과 일치). 배경을 따내는 누끼 합성은 세그멘테이션이 필요한데, 그 처리조차 이 원칙에 따라 **우리가 통제하는 실행 환경에서만** 수행해야 하므로 MVP 범위에서 제외하고 이후 검토한다.

생성 단계와의 관계: 사진이 들어갈 자리는 생성 프롬프트에 "인물 사진 배치 영역 확보" 수준의 **레이아웃 지시로만** 반영한다. 사진 자체나 얼굴 묘사를 프롬프트에 넣지 않는다.

### 분해는 시안 확정 시 한 번만 한다

규격을 바꿀 때마다 배경을 분해하고 빈 자리를 채우는 작업은 감당할 수 없다. 호출 비용도 크지만, **매번 결과가 달라져 규격 간 일관성이 깨진다.**

그래서 **④ 시안 확정 시점에 딱 한 번** 생성 이미지를 RGBA 레이어로 분해하고(Qwen-Image-Layered), 그 결과를 프로젝트의 디자인 자산으로 저장한다. 이후 모든 규격 변환은 **저장된 레이어를 재배치하는 작업**이며 분해를 다시 하지 않는다.

```
④ 확정 → 1회 분해 → [배경판, 피사체, 장식…] 저장
              ↓
   ⑥ 규격변환: 저장된 레이어를 재배치만 (분해 없음)
```

분해된 레이어는 특정 결과물이 아니라 **프로젝트 전체가 공유하는 자산**이므로 DesignAssets에 둔다(Stage 2). 포스터를 다시 만들면 레이어도 다시 분해되고, 이때 `design_updated_at`이 갱신되어 기존 결과물에 "원본 변경됨"이 붙는 기존 규칙이 그대로 적용된다.

### 이 구조가 규격 변환 문제를 푼다

PoC Q4에서 **세로 포스터를 가로 규격으로 바꿀 때 키비주얼이 잘려 사라지는 문제**를 확인했다. 통짜 이미지는 크롭밖에 할 수 없기 때문이었다.

레이어가 분리되어 있으면 다르게 처리한다.

- 배경판만 좌우로 늘리고
- 피사체는 잘라내지 않고 **왼쪽으로 옮겨** 배치하고
- 장식 요소는 규격에 맞게 생략하거나 재배치한다

**아웃페인팅 대상이 완성 포스터에서 "피사체가 빠진 배경판"으로 줄어드는 것**이 핵심이다. 배경판은 하늘·그라디언트·질감처럼 단순한 경우가 많아 확장이 훨씬 쉽고 실패 위험도 낮다. PoC에서 최대 위험으로 지목한 3-3(아웃페인팅)의 난이도가 크게 내려간다.

### 감수해야 할 것

- **분해 1회 비용이 든다.** 다만 규격마다 반복하는 것에 비하면 훨씬 싸다
- **분해 품질이 단일 실패점이다.** 잘못 분해되면 모든 규격이 영향을 받는다. 확정 전에 분해 결과를 검사하는 단계가 필요하다(피사체 개수·마스크 경계 확인, 이상 시 재분해 또는 통짜 배경으로 폴백)
- **저장 용량이 늘어난다.** 포스터 1건당 RGBA PNG가 3~6장 추가된다. 대용량 파일 보관 정책(Stage 6)의 대상이 된다

### 왜 텍스트를 하나가 아니라 둘(TITLE·INFO)로 나누는가

타이틀과 정보는 **규격이 바뀔 때 완전히 다르게 동작한다.**

- 현수막에서 타이틀은 **커지고**, 정보는 대부분 **사라진다**
- 타이틀은 어떤 규격에서도 생략되지 않는다. 정보는 `info_priority_order`대로 버려진다
- 타이틀은 그라디언트·외곽선·그림자 같은 **디자인 효과**를 받고, 정보는 가독성만 확보하면 된다
- 학습으로 도출할 값도 다르다. 타이틀은 `title_scale`, 정보는 `info_area`로 이미 따로 정의되어 있다

즉 설계상으로는 이미 나뉘어 있었고 레이어 이름만 붙지 않았던 것이다. 명시적으로 분리하면 규칙이 섞이지 않는다.

**`MARK`를 따로 둔 이유**도 같다. 로고는 텍스트가 아니라 이미지다. 폰트 렌더링이 아니라 이미지 합성이고, 가로세로 비율을 왜곡하면 안 되며 최소 표시 크기 제약이 있다. 정보 텍스트와 같은 규칙으로 다루면 로고가 찌그러진다.

### 텍스트 분리에 따른 이점

- **한 글자도 틀리지 않는다.** 기본 모드에서는 시스템이 문자열을 그대로 그리므로 오타가 원천적으로 불가능하다
- **아키텍처가 생성 모델에 종속되지 않는다.** 특정 모델의 한국어 지원 여부가 서비스 핵심 요구를 좌우하지 않는다
- **폰트를 우리가 고른다.** 브랜드 서체를 일관되게 적용할 수 있고, 장르별 서체 전략도 가능해진다
- **인쇄 품질이 보장된다.** 텍스트를 300dpi로 다시 그리므로 확대해도 선명하다

### 타이틀 생성 방식 — 두 가지 모드

타이틀이 **별도 레이어라는 점은 두 모드 모두 같다.** 그 레이어를 누가 그리느냐만 다르다.

| | **모드 A — 폰트 렌더링** (기본) | **모드 B — AI 타이포그래피** (선택) |
|---|---|---|
| 그리는 주체 | 시스템(Java2D) | Qwen-Image-3.0 |
| 오타 가능성 | **없음** | 있음 — 확정 전 육안 검수 필수 |
| 공연명 수정 | 즉시 반영 | 재생성 필요(크레딧 소비) |
| 인쇄 해상도 | 300dpi로 다시 그림, 벡터급 선명도 | 픽셀이라 업스케일 필요 |
| 표현력 | 외곽선·그림자·그라디언트 등 효과 조합 | 질감·장식·손글씨 등 폭이 넓다 |

**모드 A를 기본값으로 둔다.** 정확성과 수정 가능성이 보장되고 인쇄 품질이 가장 좋다. PoC에서 확인한 "겨울 나그네" 타이틀이 이 방식이며, 외곽선·그림자를 얹으면 밝은 배경 위에서도 안정적으로 읽힌다.

**모드 B는 표현력이 필요할 때 고르는 옵션**이다. Qwen-Image-3.0은 한국어를 포함한 12개 언어의 텍스트 렌더링을 지원한다고 명시되어 있어, 한글 타이포그래피 생성이 가능하다. 다만 실무상 주의점이 있다.

- **문자열을 따옴표로 정확히 감싸 프롬프트에 넣어야 한다.** 설명형으로 쓰면 모델이 문구를 임의로 바꾼다
- **프롬프트 자동 확장 기능을 반드시 꺼야 한다.** 켜져 있으면 문구가 재작성된다
- 약 10px까지 읽히지만 작은 글자는 해상도에 민감하다

모드 B가 성립하는 결정적 이유는 **공연명이 거의 바뀌지 않는다는 점**이다. 날짜·장소는 자주 바뀌지만 공연명이 바뀌면 사실상 다른 공연이다. 따라서 타이틀만 픽셀로 두어도 자동반영 정책에 지장이 없다. 다만 **확정 화면에서 오타를 반드시 눈으로 확인**하게 해야 한다.

투명 배경 생성은 문서에 명시되어 있지 않으므로, 타이틀을 단색 배경에 생성한 뒤 배경 제거로 분리하거나 Qwen-Image-Layered로 레이어를 뽑아내는 방식을 PoC에서 검증한다.

### 파생 규칙

- **여백 확보**: 텍스트·마크 레이어를 얹을 공간이 없으면 텍스트가 비주얼을 가린다. 생성 프롬프트에 "정보 배치 영역은 단순하게" 같은 지시를 포함한다.
- **원치 않는 텍스트 억제**: 생성 모델은 요청하지 않아도 배경에 글자 비슷한 형태를 그려 넣는 경우가 있다. 우리가 텍스트를 직접 얹으므로 **생성 이미지에는 글자가 전혀 없어야 한다.** 네거티브 프롬프트로 억제하고, 그래도 남으면 인페인팅으로 지운다.
- **object_map**: 모든 텍스트·사진·마크 요소의 좌표를 시스템이 직접 배치하므로 정확히 알고 있다. 세그멘테이션으로 되찾을 필요가 없다.
- **세그멘테이션의 역할**: ④ 확정 시 1회 분해할 때만 쓴다. 규격 변환 시점에는 저장된 레이어를 재배치할 뿐 세그멘테이션을 다시 호출하지 않는다.
- **인쇄 해상도**: 비주얼 레이어는 업스케일하고 텍스트·마크 레이어는 인쇄 해상도로 다시 렌더링해 합성한다. **PHOTO 레이어는 어느 쪽도 아니다** — 업로드 원본 파일을 인쇄 해상도로 직접 재배치한다. 사진 원본은 대체로 인쇄에 충분한 해상도이고, 부족하면 ⑧에서 해상도 경고를 띄운다(5-2). 외부 업스케일러에는 **절대 보내지 않는다** — 원칙 위반이자 얼굴 왜곡 위험이다.

## 0-2. 기술 구조 구분 — 무엇을 가져다 쓰고 무엇을 직접 만드는가

ACTSET의 기술 전략에서 가장 중요한 구분이다. 모델을 직접 만들지 않고, **공연 홍보물이라는 도메인 지식**을 자체 자산으로 축적한다.

### 외부 활용 (가져다 쓰는 것)

| 기술 | 용도 | 라이선스·형태 |
|---|---|---|
| **Tesseract OCR** | 포스터 이미지의 텍스트 추출 | Apache 2.0 오픈소스 |
| **PaddleOCR** | 텍스트 + 문서 구조 인식, 영역별 분리. 다국어 강점으로 한글 홍보물 분석 후보 | 오픈소스 |
| **Qwen2.5-VL** | 텍스트·이미지·배치관계를 함께 이해하는 VLM. "이 문구가 제목인지 날짜인지 장소인지" 역할 판정 | 오픈소스 VLM |
| **SAM2** | 인물·소품·그래픽 요소·배경을 영역 단위로 분리 | 오픈소스 세그멘테이션 |
| **Qwen-Image-Layered** | 완성 이미지를 편집 가능한 RGBA 레이어로 분해 | 오픈소스 |
| **이미지 생성 API** | 키비주얼·배경 생성 | 상용 API |
| **LLM API (GPT-5.6)** | 공연정보 구조화, 카피·상세페이지·프로그램 설명 생성 | 상용 API |
| **Cloud/Object Storage** | 프로젝트 이미지·PDF 저장 | 클라우드 서비스 |

### 자체 핵심기술 (직접 만드는 것)

1. **공연정보 구조화** — Role Schema(Stage 2)
2. **장르별 배치기준** — Genre Rules
3. **규격별 Recomposition** — Format Rules + 재배치 엔진
4. **프로젝트 관리** — 공연 단위 자산 관리와 정보 변경 반영
5. **선택데이터 기반 추천** — SelectionEvent 축적과 기준 갱신

외부 기술은 대체 가능하지만 자체 핵심기술은 대체 불가능한 자산이다. 벤더가 바뀌어도 2~5는 그대로 남도록 설계한다.

## 0-3. 레이아웃 근거 확보 전략 — 학습 기반 추천 엔진

**현재는 레이아웃을 정할 근거가 없다.** 이 문서의 GenreRule·FormatRule은 값을 담을 **구조**일 뿐이며, 그 값을 지금 임의로 정하는 것은 근거 없는 추측이다. ACTSET이 만들려는 것은 고정된 규칙표가 아니라 **포스터를 학습해 선호 레이아웃과 트렌드를 추천하는 엔진**이다.

### 3단계 성숙 과정

| 단계 | 데이터 규모 | 상태 |
|---|---|---|
| 0단계 — 현재 | 0건 | 근거 없음. PoC의 배치값은 동작 확인용 임시값이며 디자인 결정이 아니다 |
| 1단계 — 부트스트랩 | 포스터 약 **100건** | 실제 공연 포스터를 수집·분석해 장르별 초기 배치 기준을 수립 |
| 2단계 — 운영 | 수집 포스터 + 고객 데이터 최대 **10,000건** | 고객의 생성·선택·수정 데이터를 더해 기준을 갱신하고 트렌드를 반영. **여기서 '고객 데이터'는 자사가 생성한 결과물과 선택 기록이다** — 고객 업로드 원본을 외부 GPU 분석에 넣는 것은 업로드 사진 처리 원칙과 충돌하므로 Phase 3 재검토 전까지 하지 않는다 |

### 포스터 1건이 학습 데이터가 되는 과정

앞서 정리한 외부 기술이 실제로 쓰이는 지점이 여기다.

1. 포스터 이미지 입력(수집본 또는 자사 생성물. **고객 업로드 원본은 Phase 3 재검토 전까지 제외** — 업로드 사진 처리 원칙)
2. **OCR(Tesseract·PaddleOCR)** → 텍스트와 위치(bbox) 추출
3. **VLM(Qwen2.5-VL)** → 각 텍스트 덩어리의 역할 판정(제목/부제/날짜/장소/출연진/가격/주최…)
4. **SAM2** → 인물·오브젝트·장식요소 영역 분리
5. **Qwen-Image-Layered** → RGBA 레이어 분해(배경/피사체/그래픽)
6. **정규화** → 규격에 무관하게 비교 가능하도록 상대좌표로 환산 → `LayoutSample` 레코드 생성(Stage 2 참고)
7. **집계** → 장르·규격별로 역할이 놓이는 위치·크기·정렬의 분포를 구해 GenreRule·FormatRule 값으로 삼는다

이 파이프라인은 **기존 포스터 업로드 기능**(고객이 가진 포스터를 올려 편집 가능한 형태로 되살리는 기능)과 동일한 구조다. 학습용으로 만든 것이 그대로 제품 기능이 된다.

### DESIGN.md 활용

학습으로 도출한 기준은 [Google Labs의 DESIGN.md](https://github.com/google-labs-code/design.md) 포맷으로 저장한다. YAML front matter에 기계가 읽을 토큰(색상·타이포·레이아웃·간격)을 담고, 마크다운 본문에 그 값이 왜 그런지를 사람이 읽을 수 있게 적는 형식이다.

- **장르별 DESIGN.md** — 학습 결과로 만들어지는 장르 기준(클래식·어린이공연 등). 수치와 근거를 함께 담아 사람이 검수·수정할 수 있다
- **프로젝트별 DESIGN.md** — 확정된 톤앤매너(DesignAssets)를 같은 포맷으로 표현. 규격변환·추가제작물이 이 문서를 읽어 일관성을 유지한다

이 포맷을 쓰는 이유는 LLM과 코딩 에이전트가 그대로 읽을 수 있고, 값(토큰)과 근거(산문)가 한 파일에 있어 학습 결과를 블랙박스로 두지 않기 때문이다.

## 전체 파이프라인 개요 (어느 화면에서 어떤 엔진이 동작하는가)

| 화면 | 관여 엔진 | 입력 | 출력 |
|---|---|---|---|
| ③ 시안 선택 | Genre Rules + 생성 파이프라인 | PerformanceInfo, image_direction_note, reference_images | 시안 후보(포스터), object_map |
| ⑥ 일괄변환 | Format Rules + Recomposition Engine | DesignAssets, PerformanceInfo, 대상 규격(치수·비율 구간) | 규격별 후보(GeneratedAsset), object_map |
| 정보 수정 반영 | 텍스트 재렌더링(경량) | 변경된 PerformanceInfo, 기존 object_map | 포스터: 즉시 갱신 / 그 외: "최신 반영" 클릭 시 갱신 |

## 1. Genre Rules (장르별 배치 기준)

- **목적**: 장르마다 어떤 정보를 강조하는지, 출연자 노출 정도, 제목·이미지 비중, 소규격에서 생략 가능한 정보를 규칙으로 저장한다.
- **데이터 구조 제안(GenreRule)**: `{ genre, field_emphasis, default_layout_style, info_priority_order(소규격에서 먼저 생략할 필드 순서), palette_tendency, sample_count, confidence }` — **전체 필드는 Stage 12가 정본이다**
- **초기값 구축 방법**: 0-3의 3단계 성숙 과정을 따른다 — 포스터 100건 분석으로 초기값을 만들고, 이후 고객 데이터를 더해 최대 10,000건 규모로 갱신한다
- **cast.career(경력) 처리**: 클래식에서 경력 표기가 흔하다는 것은 대표자의 현장 경험에 근거한 가설이며, 실제 강조도 값은 학습 결과로 확정한다
- **값은 이 문서에서 정하지 않는다.** 이 문서는 규칙을 담는 **구조**만 정의한다. 장르 7종의 세부 값을 지금 적어 넣으면 근거 없는 수치가 사실처럼 굳어지므로, 학습 결과가 나오기 전까지 비워 둔다.

## 2. Format Rules (규격별 유지·삭제·축약·이동 기준)

- **목적**: 같은 시안을 다른 규격으로 바꿀 때 무엇을 유지·삭제·축약·이동할지 정의한다.
- **데이터 구조 제안(FormatRule, 비율 구간별 — Stage 12 참고)**: `{ crop_strategy, title_area, title_scale, title_effect, info_area, photo_area, mark_area, body_scale, min_readable_px, align, max_blocks, info_priority_order, session_display, undetermined_copy }` — **전체 필드는 Stage 12가 정본이다.** 인쇄 재단여백은 규격 속성이 아니라 인쇄 시점에 적용하는 처리이므로 FormatRule에 두지 않는다
- **회차 표시 규칙**: Stage 2에서 예고한 대로, 규격별로 sessions 전체 나열(상세페이지형) vs 기간 요약(포스터형) 중 무엇을 쓸지 여기서 규격마다 확정한다.
- **인쇄는 규격 변환의 한 형태**: 인쇄 가능 여부를 규격별로 나누지 않는다(`is_print_target` 폐기). 어떤 결과물이든 인쇄 크기(mm)와 dpi를 정하면 레이어 스택을 그 치수로 다시 합성한다. CMYK·재단여백은 규격 속성이 아니라 **인쇄 시점에 적용하는 처리**다. 실제 PDF 변환 로직(Print Engine)은 Phase 6 구현 대상이다(Stage 12 참고).

### 정보 포함·생략 우선순위 규칙 (충돌 해소)

규격이 작아 모든 정보를 담을 수 없을 때 아래 순서로 판단한다. 위쪽이 우선한다.

1. **사용자의 명시적 제외 지시** — `image_direction_note`에 "이 시안에는 날짜를 넣지 말아달라"처럼 특정 정보를 빼달라는 지시가 있으면 무조건 따른다. 미정 필드의 대체 문구("일정 추후 공지")도 이 지시가 있으면 넣지 않는다.
2. **필수 안내문구(`mandatory_notices`)** — 저작권·후원사·법적 고지 등은 `info_priority_order`의 생략 대상에서 **제외**한다. 공간이 부족하면 다른 정보를 먼저 줄인다.
3. **필수 4항목**(장르 제외: 공연명·날짜·장소) 및 미정 대체 문구
4. **`info_priority_order`에 따른 나머지 정보** — 공간이 부족한 순서대로 생략·축약

**예외 처리**: 2번 필수문구까지 넣어도 최소 가독 크기(`min_readable_px`)를 확보할 수 없는 규격(현수막·썸네일 등)에서는 자동으로 지우지 않고, 결과물에 "이 규격에는 필수문구를 모두 넣기 어렵습니다" 경고를 표시해 사용자가 직접 판단하도록 한다. 필수문구는 법적·계약적 의무일 수 있어 시스템이 임의로 생략해서는 안 된다.

## 3. Recomposition Engine (규격별 자동 재배치)

- **입력**: DesignAssets의 **분해된 레이어 스택**, PerformanceInfo, 대상 규격(치수), 해당 비율 구간의 FormatRule
- **처리 단계(제안)**
  1. 저장된 레이어 스택과 object_map 로드 (**분해를 다시 하지 않는다**)
  2. `BACKDROP`을 대상 비율로 확장·크롭. 비율 차가 크면 이때만 아웃페인팅
  3. `SUBJECT`·`DECOR`를 새 캔버스에 재배치 — 잘라내지 않고 옮긴다
  4. `PHOTO`를 photo_area 기준으로 재배치 — 비율·마스크를 유지하고, 공간이 부족한 소규격에서는 개수를 줄이거나 생략한다
  5. 텍스트 레이어는 FormatRule의 title_scale·info_priority_order 적용
  6. 정보 밀도가 초과되면 info_priority_order 순서대로 항목을 생략·축약
  7. 규격별 3안 생성 — 레이어 배치 파라미터를 다르게 해 여러 안을 만든다(생성 API 재호출 없이 배치만 달리하므로 비용이 거의 들지 않는다)
- **출력**: GeneratedAsset(image_url, object_map)

## 4. 생성 파이프라인 (외부 AI 기술 매핑)

이전 리서치에서 검토했던 MVP 스택을 기준으로 정리한다. 실제 벤더는 Stage 7에서 최종 확정한다.

| 단계 | 기술(검토 스택) | 역할 |
|---|---|---|
| ③ 초기 시안 생성 | 이미지 생성 API(Ideogram 4.0) | 비주얼 생성 — **글자 없는 순수 이미지** |
| ④ 레이어 분해 (1회) | **Qwen-Image-Layered** | 생성 이미지를 배경판·피사체·장식 RGBA 레이어로 분해해 저장 |
| 타이틀(모드 B, 선택) | **Qwen-Image-3.0** | 한국어 포함 12개 언어 텍스트 렌더링. 타이포그래피를 이미지로 생성 |
| 텍스트 렌더링 | **자체 렌더링(Java2D)** | TITLE·INFO 레이어 폰트 렌더링 및 합성 — 벤더 의존 없음 |
| 업로드 사진 합성 | **자체 렌더링(Java2D)** | PHOTO 레이어 액자형 배치·합성 — **외부 전송 없음** |
| 참고 이미지 분석 | VLM(Qwen2.5-VL) | reference_images의 구도·스타일·요소 역할 분석 → 생성 프롬프트에 반영. **인물 사진은 대상이 아니다** — 참고 이미지는 스타일 참고를 전제로 하며, 업로드 시 안내한다 |
| 기존 포스터 분석 | OCR(Tesseract·PaddleOCR) + VLM(Qwen2.5-VL) | 텍스트 추출 및 역할 판정 — 학습 파이프라인과 업로드 기능에 공통 사용 |
| 요소 분리 | SAM2 | 인물·소품·그래픽·배경 영역 분리 |
| 기존 포스터 레이어화 | Qwen-Image-Layered | 고객 업로드 포스터를 편집 가능한 형태로 복원(Phase 3+). **고객 업로드물의 외부 전송을 전제하므로 위 원칙과 충돌한다** — Phase 3 설계 시 자체 실행 환경 또는 별도 동의 방식으로 재검토 |
| 배경 보정·확장 | 인페인팅·아웃페인팅 | 세로→가로처럼 비율이 크게 바뀔 때 배경 확장 |
| 인쇄용 업스케일 | 업스케일러 | 비주얼 레이어를 인쇄 해상도로 확대(텍스트 레이어는 재렌더링) |
| 기존 포스터 텍스트 추출 | OCR(PaddleOCR 등) | Genre Rules 부트스트랩 리서치에서 실제 포스터의 텍스트 위치·비중 추출 |
| 소개문·카피 보조 | **GPT-5.6** | introduction/synopsis 초안 보완(MVP는 최소 범위로 제한, 본격 활용은 Phase 4 상세페이지) |

## 5. SelectionEvent 활용 (추천 고도화 루프)

수집(Stage 2에서 이미 확정) → 분석(화면·generation_params별 선택률·재생성률 집계) → Genre/Format Rules 파라미터 조정 → 추천 품질 개선 → 재생성 감소, 순으로 이어진다. MVP 기간에는 데이터 **수집**까지만 하고, 이를 규칙에 자동 반영하는 학습 파이프라인은 사업계획서 Phase 7(데이터·글로벌 단계)로 이연한다. 지금은 "무엇을 위해 수집하는지" 구조만 정의한다.

## 6. 시안 후보 개수 (Stage 3에서 이월된 결정)

- **트레이드오프**: 후보가 많을수록 선택 만족도는 오르지만 API 비용도 함께 오른다.
- **확정**: MVP는 3개로 한다. "다른 방향 보기"가 별도로 추가 후보를 요청하는 구조이므로 초기 3개로도 충분히 시작할 수 있다. 재생성·이 방향으로 더 보기도 1~2개 단위로 제한해 비용을 통제한다.

## 확인이 필요한 사항

1. Genre Rules 초기값을 만들 부트스트랩 리서치(실제 포스터 다수 분석)는 이 기획 문서 범위 밖의 별도 작업이다 — 언제·몇 건으로 진행할지 확인 필요
2. Recomposition에서 규격별 3안을 API 다회 호출로 만들지, 1회 생성 후 배치 변형만 다르게 할지는 실제 이미지생성 API 벤더 선정 후 재검토 필요
3. LLM 기반 카피 생성을 MVP에서 어느 수준까지 넣을지(단순 요약만 vs 초안 제안까지) — 본격 활용은 Phase 4(상세페이지)이므로 MVP는 최소 범위를 제안하나 확인 필요
