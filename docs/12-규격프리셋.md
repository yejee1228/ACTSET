# 규격 프리셋 · 룰 스키마 (Stage 12)

> **치수는 확정, 배치 규칙의 값은 비워 둔다.** 규격 치수는 매체가 정한 값이라 학습과 무관하게 확정할 수 있지만, 배치 기준은 포스터 학습으로 도출되어야 한다(Stage 5의 0-3).

## 1. 기본 규격 상수

테이블이 아니라 **애플리케이션 상수(enum)**로 둔다(Stage 2·10). 커스텀 규격은 결과물이 `format_code='CUSTOM'`과 실제 치수를 직접 들고 있으므로 여기에 추가되지 않는다.

| code | label | 치수(px) | group | 비고 |
|---|---|---|---|---|
| `POSTER` | 포스터(세로) | 1240 × 1754 | 원본 | A4 비율. 프로젝트당 1건의 대표 이미지 |
| `NOL_TICKET` | NOL티켓 대표이미지 | 750 × 1000 | 예매처 | 3:4 |
| `TICKETLINK` | 티켓링크 대표이미지 | 720 × 960 | 예매처 | 3:4 |
| `PLAY_TICKET` | 플레이티켓 대표이미지 | 400 × 600 | 예매처 | 2:3 |
| `SNS_1X1` | SNS 1:1 | 1080 × 1080 | 온라인 | 인스타그램 정사각 |
| `SNS_4X5` | SNS 4:5 | 1080 × 1350 | 온라인 | 인스타그램 세로 |
| `STORY` | SNS 스토리 | 1080 × 1920 | 온라인 | |
| `WEB_THUMB` | 홈페이지 썸네일 | 940 × 440 | 온라인 | |
| `WEB_BANNER` | 홈페이지 배너 | 1920 × 600 | 온라인 | |
| `DID` | DID | 1080 × 1920 | 온라인 | 세로형 디지털 사이니지 |
| `HALL_MONITOR` | 공연장 모니터 | 1920 × 1080 | 온라인 | |
| `BANNER_WIDE` | 현수막(가로) | 2048 × 256 | 오프라인 | 화면 미리보기용 비율. 인쇄는 아래 참조 |
| `X_BANNER` | X배너 | 600 × 1800 | 오프라인 | 실물 600 × 1800mm |

**원본 1종 + 변환 대상 12종**이다. `예매처` 그룹을 별도로 둔 이유는 ⑤ 화면에서 사용자가 자기가 쓰는 예매처만 고르면 되도록 묶어 보여주기 위해서다.

> **제거된 규격**: 기존 목록에 있던 `TICKET_SITE`(예매처 이미지, 652×423)는 PoC 단계에서 **임의로 만든 값**이었고, 실제 예매처 규격이 확인되면서 삭제하였다. 실제 예매처 대표이미지는 모두 세로형(3:4·2:3)이라 가로형이었던 기존 값은 근거가 없었다.
>
> **추가 확인 필요**: 예스24 공연·멜론티켓 등 다른 예매처 규격은 확인 후 같은 방식으로 추가한다. 규격이 상수이므로 코드 한 줄 추가로 끝난다.

### 인쇄 — 모든 규격이 대상이다

**규격별로 인쇄 가능 여부를 나누지 않는다.** SNS 이미지를 엽서로 뽑든 스토리 규격을 배너로 뽑든 막을 이유가 없다. 따라서 이전 표에 있던 `is_print_target` 플래그는 **폐기한다.**

대신 인쇄를 **또 하나의 규격 변환**으로 취급한다. 화면용 픽셀 규격과 인쇄용 물리 규격(mm)은 애초에 다른 축이고, 레이어 스택이 있으므로 어떤 결과물이든 원하는 인쇄 크기로 다시 합성할 수 있다(Stage 5).

```
결과물 선택(어떤 규격이든)
  → 인쇄 크기 선택 (A4 / A3 / 현수막 / 직접 입력 mm)
  → 해당 mm × dpi로 레이어 재합성
       · 비주얼 레이어: 업스케일
       · 텍스트·마크 레이어: 인쇄 해상도로 재렌더링
  → 재단여백 · CMYK 적용 → 인쇄 PDF
```

이 구조에서는 인쇄 크기가 미리 정해진 목록에 갇히지 않는다. 사용자가 "가로 5m 현수막"을 요청하면 그 치수로 재합성하면 된다.

### 인쇄 해상도 기준

멀리서 보는 인쇄물에 300dpi는 불필요하다. 관람 거리에 따라 기준을 나눈다.

| 용도 | 기준 dpi | 재단여백 | 근거 |
|---|---|---|---|
| 포스터·리플렛·엽서 (가까이 봄) | 300 | 3mm | 일반 인쇄 표준 |
| X배너·등신대 (1~2m) | 150 | 10mm | |
| 현수막 (5m 이상) | 100~150 | 20mm | 대형일수록 낮춰도 무방 |

예시: A3 포스터 300dpi = 3508 × 4961px, 5000×700mm 현수막 150dpi = 29528 × 4134px.

**실제 값은 인쇄 협력업체 협의 후 확정한다.** 업체마다 요구하는 재단여백과 최소 해상도가 다르다.

### 비율이 맞지 않는 경우

결과물의 비율과 인쇄 크기의 비율이 다르면 여백이 생기거나 잘린다. 이때도 **레이어를 재배치해 대응**하며, 대응이 어려우면 경고를 표시하고 사용자가 판단하도록 한다(Stage 3·4의 인쇄 경고 규칙과 동일).

## 2. FormatRule 스키마 (값은 비움)

규격별 배치 기준을 담을 구조다.

```jsonc
{
  "format_code": "SNS_1X1",
  "title_area":     null,   // TITLE — 타이틀 영역 [x0,y0,x1,y1]
  "title_scale":    null,   // TITLE — 짧은 변 대비 제목 크기 비율
  "title_effect":   null,   // TITLE — 외곽선/그림자/글로우 강도
  "info_area":      null,   // INFO — 정보 영역 [x0,y0,x1,y1]
  "photo_area":     null,   // PHOTO — 업로드 사진 배치 영역·최대 개수
  "mark_area":      null,   // MARK — 로고 배치 영역·최소 크기
  "body_scale":     null,   // 본문 기본 크기 비율
  "min_readable_px": null,  // 이보다 작아지면 생략 판단
  "align":          null,   // left | center | right
  "max_blocks":     null,   // 표시할 최대 정보 블록 수
  "crop_strategy":  null,   // 배경 크롭 기준
  "info_priority_order": null,  // 공간 부족 시 생략 순서
  "session_display": null,  // 회차 전체 나열 vs 기간 요약
  "undetermined_copy": {    // 미정 대체 문구 — 학습 대상이 아니므로 지금 정할 수 있다
    "date": "일정 추후 공지",
    "venue": "장소 추후 공지"
  }
}
```

`undetermined_copy`만 값이 채워져 있다. 나머지는 학습 결과가 나온 뒤 채운다.

### 규칙은 규격이 아니라 비율에 붙인다

규칙을 `format_code`에만 매달면 **커스텀 규격에는 적용할 규칙이 없다.** 사용자가 1200×400을 입력하면 어떤 배치를 써야 할지 알 수 없다.

그런데 배치를 실제로 좌우하는 것은 규격 이름이 아니라 **화면 비율**이다. 1080×1080과 2000×2000은 같은 배치를 쓴다. 학습 데이터인 LayoutSample도 이미 `aspect_ratio`로 정규화되어 있다.

따라서 규칙을 **비율 구간(bucket)**에 붙이고, 기본 규격은 각자 해당하는 구간을 가리키게 한다.

| 구간 | 비율 범위 | 해당 기본 규격 |
|---|---|---|
| `TALL` | 세로 1:1.15 ~ 1:1.55 | POSTER(1:1.41), SNS_4X5(1:1.25), NOL_TICKET·TICKETLINK(1:1.33), PLAY_TICKET(1:1.5) |
| `EXTRA_TALL` | 세로 1:1.55 이상 | STORY·DID(1:1.78), X_BANNER(1:3) |
| `SQUARE` | 0.87 ~ 1.15 | SNS_1X1(1:1) |
| `WIDE` | 가로 1.15:1 ~ 2.5:1 | HALL_MONITOR(1.78:1), WEB_THUMB(2.14:1) |
| `EXTRA_WIDE` | 가로 2.5:1 ~ 5:1 | WEB_BANNER(3.2:1) |
| `ULTRA_WIDE` | 가로 5:1 이상 | BANNER_WIDE(8:1) |

각 규격의 실제 비율을 괄호에 적었다. **경계값은 모든 기본 규격이 정확히 한 구간에만 속하도록 잡은 것**이며, 학습 표본 분포를 본 뒤 조정한다.

커스텀 규격은 비율을 계산해 가장 가까운 구간의 규칙을 쓴다. 규칙 수도 13개에서 6개로 줄어 **학습에 필요한 표본이 구간별로 모인다.** 규격마다 따로 학습하면 표본이 흩어져 근거가 약해진다.

구간 경계값은 임시이며, 실제 표본 분포에서 배치가 갈리는 지점을 보고 조정한다.

**PoC의 값을 옮겨 적지 않는다.** `poc/engine.py`의 `RULES`는 엔진 동작 확인용 임시값이며, 여기에 복사하면 근거 없는 수치가 확정값처럼 굳는다.

## 3. GenreRule 스키마 (값은 비움)

```jsonc
{
  "genre": "클래식",
  "field_emphasis": {
    // 역할별 강조도: 필수표시 | 기본표시 | 선택표시 | 기본숨김
    "cast": null, "cast.career": null, "price": null,
    "organizer": null, "age": null, "running_time": null, "program": null
  },
  "default_layout_style": null,   // 제목·이미지 비중, 여백 성향
  "info_priority_order": null,    // 이 장르에서 무엇을 먼저 버리는가
  "palette_tendency": null,       // 색 성향
  "sample_count": 0,              // 근거가 된 LayoutSample 수
  "confidence": null              // 표본이 적으면 낮게
}
```

`sample_count`와 `confidence`를 규칙 자체에 넣은 이유는, **표본이 몇 건인지 모르는 규칙을 신뢰해서는 안 되기 때문**이다. 표본이 부족한 장르는 화면에서 추천 강도를 낮추거나 사용자에게 선택지를 더 넓게 제시하는 식으로 다르게 다룬다.

### 값을 채우는 방법

Stage 5의 학습 파이프라인이 `layout_samples`를 쌓으면, 장르별로 다음을 집계해 값을 만든다.

| 규칙 항목 | 집계 방법 |
|---|---|
| `field_emphasis.X` | 해당 장르 표본 중 역할 X가 `present_roles`에 포함된 비율 |
| `info_area`* | 텍스트 역할들의 상대좌표 분포에서 중앙값 영역 |
| `title_scale`* | 제목 역할의 `font_size_ratio` 중앙값 |
| `info_priority_order` | 소규격 표본에서 먼저 사라지는 역할 순서 |
| `palette_tendency` | `palette` 군집화 |

\* `info_area`·`title_scale`은 GenreRule이 아니라 **FormatRule(비율 구간별) 필드**다. 같은 집계 파이프라인에서 산출하되 장르가 아니라 비율 구간으로 묶어 저장한다.

집계 기준(중앙값·분위수·이상치 제거)은 실제 표본 분포를 본 뒤 정한다. 지금 정하면 데이터를 보기 전에 방법을 고정하는 셈이 된다.

## 4. DESIGN.md 포맷 적용

학습 결과와 프로젝트 톤앤매너를 [DESIGN.md](https://github.com/google-labs-code/design.md) 형식으로 저장한다. YAML front matter에 기계가 읽을 토큰을, 본문에 사람이 읽을 근거를 담는다.

### 장르별 — `genres/classical.DESIGN.md`

```markdown
---
name: ACTSET 클래식 배치기준
tokens:
  typography:
    title_scale: null        # 학습 후 확정
  layout:
    info_area: null
  emphasis:
    cast_career: null
meta:
  sample_count: 0
  updated_at: null
---

## Overview
클래식 공연 포스터의 배치 경향. 값은 LayoutSample 집계로 산출한다.

## Typography
(표본 확보 후 작성)

## Do's and Don'ts
(표본 확보 후 작성)
```

### 프로젝트별 — `projects/{id}.DESIGN.md`

확정된 DesignAssets를 같은 형식으로 표현한다. 규격변환·추가제작물이 이 문서를 읽어 톤을 유지하고, LLM이 카피를 쓸 때도 같은 문서를 참조한다.

이 포맷을 쓰는 실질적 이유는 **학습 결과를 블랙박스로 두지 않는 것**이다. 수치만 있으면 왜 그런지 알 수 없고 사람이 고칠 수도 없다. 근거를 산문으로 함께 적어 두면 디자인 자문이 검수할 수 있고, 이상한 값이 나왔을 때 원인을 추적할 수 있다.

## 5. 지금 확정 가능한 것과 아닌 것

| 항목 | 상태 |
|---|---|
