## 1. 관리자 백오피스 — 가장 큰 구멍

Stage 1·6·11이 모두 **"베타는 관리자 지급 크레딧으로 운영한다"**를 전제로 하는데, 그 지급을 수행할 도구가 어디에도 없었다. DB에 `admin_grant` 타입만 있고 화면도 티켓도 없다.

**최소 기능**

- 계정 조회 / 크레딧 수동 지급·회수 (사유 기록 필수)
- 실패한 job 목록 조회 · 강제 재시도 · 강제 환불
- 프로젝트·생성물 조회 — "제 포스터가 안 나와요" 문의에 답하려면 필요
- 관리자 행위 감사 로그

권한 구분을 위해 `accounts.role`(user/admin) 컬럼을 Stage 10에 추가했다.

**주의**: 관리자가 고객의 생성물을 열람할 수 있다는 사실은 개인정보처리방침에 명시해야 하고, 열람 이력을 남겨야 한다.

## 2. 법적 요구사항 (한국)

기획 전체에서 "동의"·"사업자"·"청약철회"가 한 번도 등장하지 않았다. 이 영역이 백지였다.

### 개인정보 수집 시점부터 (= 베타부터) 필수

| 항목 | 내용 |
|---|---|
| 개인정보처리방침 게시 | 수집 항목, 목적, 보유기간, 파기절차, 제3자 제공, 처리위탁, 정보주체 권리, 보호책임자 연락처 |
| 수집·이용 동의 UI | **필수 동의와 선택 동의(마케팅) 분리.** 동의 일시·문서 버전 저장 (Stage 10 `terms_agreed_at` 등) |
| 처리위탁·**국외이전 고지** | 아래 별도 항목 |
| 개인정보 보호책임자 지정·표기 | |
| 접속기록 보관 | 개인정보처리시스템 접속기록 최소 1년 보관·정기 점검 |

### 국외이전 — 설계로 대부분 해소, 남는 것은 텍스트

**업로드 사진(출연진·공연 사진)은 외부 AI API로 전송하지 않는다**는 설계 원칙이 확정되었다(Stage 5). 인물 사진이 해외 서버로 나가지 않으므로, 국외이전 리스크의 가장 큰 부분이 고지·동의가 아니라 **아키텍처로** 해소된다. 단 **예외가 하나 있다** — 참고 이미지(reference_images)는 스타일 분석을 위해 VLM(서버리스 GPU)으로 전송된다(아래 표).

그래도 해외로 나가는 것이 남아 있다.

| 전송 대상 | 어디로 | 담길 수 있는 개인정보 |
|---|---|---|
| 공연 소개문·시놉시스 (다듬기 요청 시) | GPT-5.6 (미국) | **출연진 이름·경력** — 개인정보다 |
| 생성 프롬프트 | Ideogram (미국) | 구조화 필드(출연진 이름 등)는 프롬프트 빌더에 입력되지 않도록 **타입으로 차단**(Stage 5). 단 자유서술(image_direction_note)에 사용자가 직접 쓴 이름은 막을 수 없다 — **고지로 커버** |
| **참고 이미지(reference_images)** | 서버리스 GPU (미국) — VLM 스타일 분석 | 인물 사진이 아닌 스타일 참고를 전제로 하나 **사용자가 인물 사진을 올리는 것을 막을 수 없다.** 업로드 시 "외부 분석에 전송됨, 인물 사진은 넣지 말 것" 안내 + 고지문 포함 |
| 수집 포스터 100건 (학습 파이프라인) | 서버리스 GPU (미국) | 공개된 포스터 — 고객 데이터 아님. 저작권 이슈로 별도 관리(0-3) |

따라서 남는 실무는 둘이다.

- **국외이전 고지** — 소개문·시놉시스의 출연진 이름(GPT-5.6), 참고 이미지(VLM 분석), 그리고 자유서술인 image_direction_note가 프롬프트에 반영되어 전송될 수 있음을 처리방침에 명시하고, 이전받는 자·국가·항목·목적·보유기간을 기재한다. 각 벤더의 학습 데이터 이용 여부 확인·옵트아웃 포함(Stage 14 E0)
- **원칙의 코드 강제** — 업로드 사진과 프롬프트가 외부로 나가는 코드 경로가 생기지 않도록, 외부 API 어댑터의 입력 타입에서 사진·개인정보 필드를 원천 배제한다. 리뷰 규칙이 아니라 타입으로 막는다

**Phase 3+의 "기존 포스터 업로드" 기능은 이 원칙과 충돌한다.** 고객이 올린 포스터(얼굴 포함 가능)를 Qwen-Image-Layered로 보내는 구조이므로, 그 시점에 자체 실행 환경 전환 또는 별도 국외이전 동의를 다시 설계해야 한다.

### 유료 결제 시작 시점부터 필수

| 항목 | 내용 |
|---|---|
| 통신판매업 신고 + 사업자정보 표시 | 상호·대표자·사업자등록번호·신고번호·주소·연락처·호스팅 제공자를 푸터에 표시. **푸터 기획 자체가 없었다** |
| 청약철회·환급 규정 | 디지털 콘텐츠는 제공 개시 시 철회 제한 예외가 있으나, **사전 고지와 시용 수단 제공이 있어야 유효하다.** 충전 크레딧과 소비된 크레딧을 나눠 규정 |

| 선불충전금 성격 검토 | 크레딧 선판매 + 유효기간 없음 조합. 규모가 커지기 전에 확인하는 편이 싸다 |

### 권장

- **광고성 정보 전송**(정보통신망법) — 사전 동의, 제목에 (광고) 표기, 수신거부 방법, 야간 전송 제한, 2년마다 수신동의 확인. 아래 리텐션 메일 계획과 함께 설계

## 3. AI 서비스 특유의 문제

### 부적절 콘텐츠 생성 차단 — 필수

`image_direction_note`가 **자유 서술 필드이고 그대로 생성 프롬프트에 반영된다.** 사용자가 무엇이든 요청할 수 있는 구조다. 유료 서비스에서 성인물·폭력물·실존 인물 딥페이크가 생성되면 즉시 서비스 존립 문제가 된다.

- 입력 프롬프트 금칙어·패턴 필터 (`image_direction_note`, `main_title`, `mandatory_notices`)
- **벤더의 정책 위반 거부 응답 처리** — 현재는 job failed로 뭉뚱그려져 크레딧은 환불되지만 사용자는 이유를 모른다. 별도 오류 코드와 안내 문구가 필요
- 반복 위반 계정 차단 (관리자 기능)
- 업로드 이미지 검사 방침

### 생성물 소유권·이용범위 — 필수

사용자는 결과물을 **인쇄해 공연장에 걸고 예매처에 올린다.** 상업적 이용이 전제인데 권리 관계가 약관에도 UI에도 없었다.

- 사용자에게: 결과물 이용권 범위(상업적 이용 허용 여부, 재판매 금지 등)
- 벤더에게: 요금제별 상업 이용 권한과 생성물 소유권 조항 확인(Stage 14 E0)
- 사용자 업로드물의 권리 보증 — 남의 사진·로고를 올릴 수 있으므로, 권리 보유와 **출연진 초상권 동의 확보 책임**을 사용자에게 두는 조항 필요

### 외부 API 장애 대응 — 필수

현재는 job 재시도와 30분 후 pending 복구뿐이다.

- HTTP 타임아웃, 지수 백오프, 재시도 상한
- **재시도 가치가 있는 실패와 없는 실패의 구분** — 정책 위반은 재시도해도 무의미하다
- Ideogram 단일 벤더 의존이므로 장애 = 시안 생성 전면 중단. 사용자 안내 배너와 크레딧 즉시 환불 보장
- 벤더 장애 시 대체 경로 검토(Stage 14)

### 권장

- **생성 실패 UX 구체화** — 실패 사유 문구 매핑(내부 에러 메시지 노출 금지), 자동 재시도 중 화면 표시, **환불되었다는 사실의 명시적 안내**(현재는 조용히 환불되어 사용자는 크레딧이 사라진 줄 안다)
- **소요시간 기대치 관리** — 진행 단계 표시(배경 생성 중 → 레이어 분해 중 → 텍스트 합성 중). 수 분 걸리는 작업에서 이탈률을 좌우한다
- **저작권 분쟁 대응 절차** — 침해 신고 창구, 생성물 삭제·차단 절차, 학습 데이터 제외 요청 처리, 약관상 책임 범위. `generation_params`가 저장되므로 근거 데이터는 있다
- **AI 모델 버전 고정** — 벤더가 모델을 바꾸면 "다시 만들기" 결과의 톤이 달라진다. 톤앤매너 일관성이 핵심 가치이므로 `generation_params`에 모델 버전을 반드시 포함시킨다

## 4. 빠진 화면·기능

### 필수

| 화면 | 왜 |
|---|---|
| **비밀번호 찾기·재설정** | 없으면 비번을 잊은 사용자는 계정과 프로젝트 전체를 영구히 잃는다. 문의 창구도 없어 복구 경로가 아예 없다 |
| **계정 설정** | 탈퇴 로직은 있으나 실행할 화면이 없다. 이메일·비밀번호 변경, 로그아웃 포함 |
| **오류·예외 화면** | 404/500, 네트워크 끊김, **세션 만료(입력 도중 401 → 입력값 유실)**, 생성 실패 카드, 잔액부족 402 모달. 현재 정의된 빈 상태는 홈 대시보드 하나뿐 |
| **고객 문의 창구** | 티켓의 "피드백 수집 채널"은 인터뷰 접점이지 상시 창구가 아니다. 유료 출시 시엔 연락처 표시가 법적 의무이기도 하다 |
| **진행 중 작업 안내** | 완료 감지가 폴링뿐이라 탭을 닫으면 알 수 없다. "브라우저를 닫아도 대시보드에서 확인 가능" 안내 + 재진입 시 진행중 작업 표시 |

### 권장

- **이메일 인증** — 오타 메일 가입 시 재설정 불가. 무료 크레딧이 지급되므로 대량 가짜 계정 어뷰징 통로가 된다
- **온보딩** — 성공기준이 "완주율"인데 완주를 돕는 장치가 없다. "미정", "최신 반영", "원본 다시 만들기", "크레딧" 등 처음 보는 개념이 많다
- **도움말·FAQ** — 특히 크레딧 소비 이유, "왜 다른 홍보물은 자동으로 안 바뀌나", 다운로드 90일 만료 — 문의가 반드시 발생하는 세 지점
- **반응형 대응 범위 결정** — Stage 4가 "Stage 7에서 결정"으로 넘겼는데 어디에도 없다. 공연 기획자는 현장에서 폰으로 결과물을 확인·전달한다. 최소한 ⑦ 대시보드와 다운로드는 정해야 한다
- **소셜 로그인(카카오)** — 스키마만 열려 있고 기획이 없다. 국내 서비스에서 가입 전환율 차이가 크다
- **공지 기능** — 점검·가격 변경·약관 변경 고지 수단

## 5. 기술 운영

### 필수

**보안 기본 항목** — 현재 "세션 인증·404 은닉·서명 URL" 세 줄이 전부다.

- **파일 업로드 검증** — MIME·매직바이트 검증, 크기 제한, 확장자 화이트리스트, **이미지 재인코딩(EXIF 제거 포함)**. 원격 코드 실행·저장소 남용의 직접 경로다
- **CSRF 방어** — 세션 쿠키 인증을 택했으므로 필수
- 비밀번호 정책·해싱 알고리즘, 로그인 브루트포스 제한
- **API 레이트리밋** — 특히 생성 엔드포인트
- 시크릿 관리 — Ideogram·GPU·S3 키가 코드에 들어가면 안 된다

**비용 폭주 방지** — 베타는 크레딧을 넉넉히 지급하므로 크레딧이 실질 통제 수단이 아니다.

- 계정별 시간당 생성 횟수 상한
- 전체 일일 외부 API 호출 예산 상한, 초과 시 자동 차단
- 누적 비용 대시보드와 임계 알림

**테스트 전략** — 전 문서에 없었다.

- **크레딧 트랜잭션 테스트** — 동시 요청, 부분 실패 환불, 중복 차감 방지. 돈이 걸린 로직인데 검증 계획이 없다
- **렌더링 골든 이미지 테스트** — 이미지 출력은 깨져도 컴파일이 통과한다. 픽셀 diff 비교 필요
- **외부 AI API 목킹** — 없으면 테스트마다 실제 과금된다

**배포 전략**

- 환경 분리(dev/staging/prod), CI, Flyway 마이그레이션과 배포 순서, 롤백 절차
- **worker graceful shutdown** — 작업 처리 중 배포되면 job이 running 상태로 고아가 된다. 30분 복구 배치가 덮지만 그동안 사용자는 멈춘 화면을 본다

### 권장

- **모니터링** — 헬스체크, 에러 수집(Sentry 등), 큐 적체 감시(pending job 수), 외부 API 응답시간·실패율·누적 비용, **알림 수신 채널**(현재 "실패 작업 알림"을 어디로 보낼지 정해져 있지 않다)
- **로깅 표준** — 로그 레벨, 요청 추적 ID(비동기 job까지 이어지는 상관관계 ID), 개인정보 마스킹, 보관기간, 감사 로그. 접속기록 1년 보관 의무와 연결된다
- **백업·복구** — RDS 자동백업·PITR 설정과 **복구 리허설**. 그리고 **S3 백업 정책이 아예 없다.** 이 서비스의 실질 자산은 DB가 아니라 S3의 이미지 파일이다. 버저닝·삭제방지 필요
- **삭제 배치 안전장치** — 정리 배치가 파일을 하드 삭제하므로 **배치 버그 하나가 고객 자산을 영구 파괴할 수 있다.** 드라이런 모드, 건수 상한, 실행 결과 알림을 반드시 넣는다
- **장애 대응 런북** — 외부 API 다운, 워커 정지, DB 장애 시 절차와 사용자 고지 수단(점검 배너 기능 자체가 없다)
- **스토리지 용량·비용 추정** — 프로젝트당 예상 용량 × 사용자 수. 90일 만료 정책의 실제 효과를 알 수 없는 상태다

## 6. 비즈니스 운영

### 필수 — 퍼널 이벤트 수집

Stage 1의 성공 기준이 "정보입력 → 시안생성 → 선택 완료율"과 "다운로드율"인데, **SelectionEvent는 ③·⑥의 생성 액션만 기록한다.** 화면 진입·이탈·다운로드 이벤트를 담는 구조가 없어 **성공 기준을 측정할 수 없다.**

- 방문 → 가입 → 첫 프로젝트 → ① → ② → ③ → ④ → ⑤ → ⑥ → 다운로드 단계별 이벤트 정의
- **②(9개 그룹 입력)의 이탈 지점** — 가장 이탈이 많을 화면인데 관측 수단이 없다
- 분석 도구 도입 여부(GA4 · Amplitude · PostHog) 또는 자체 이벤트 테이블
- **크레딧 소비 분포 집계** — Stage 6이 "베타에서 액션별 소비 분포를 관측해 단가 근거로 삼는다"를 명시적 목표로 두는데, 집계 화면·쿼리가 정의되지 않았다. **베타의 핵심 목적이 측정 불가 상태다**

### 권장

- **소개 페이지 SEO** — Vite SPA를 택하며 "SEO 불필요"로 판단했으나, 소개 페이지는 **유일한 유입 관문**이다. 메타·OG 태그, 정적 렌더링, UTM 추적은 필요하다
- **가입 전 체험 경로** — 현재는 가입해야만 결과를 볼 수 있다. 장르별 샘플 갤러리 또는 1회 체험
- **리텐션** — 이 서비스는 사용 주기가 길다(공연 단위). "쓰지 않는 달에 요금이 안 나간다"를 장점으로 내세우므로 **가만두면 잊혀지는 구조**다
  - 미완료 draft 리마인드 — 현재는 30일 후 조용히 삭제할 뿐. 회수가 가장 쉬운 지점이다
  - 다운로드 만료 임박(90일) 알림 — 현재는 만료 후에야 알게 된다
  - 공연일 임박 → 추가 홍보물 제작 유도
  - 모두 메일 발송 인프라에 의존한다
- **B2B 문의 접점** — 수익 구조 네 축 중 하나인데 문의 창구가 없다
- **"두 번째 프로젝트" 지표 산식** — Stage 6이 장기 성장 기준으로 재정의했으나 측정 방법이 없다

## 7. 티켓 배치 제안

Stage 13에 다음 티켓을 추가한다.

| 에픽 | 추가 티켓 |
|---|---|
| **E0** | 약관·개인정보처리방침 작성 / 국외이전 고지 범위 확정 / 벤더 상업이용·소유권 조항 확인 / 생성물 이용범위 규정 |
| **E1** | 메일 발송 인프라 / 비밀번호 재설정 / 계정 설정 화면 / 가입 동의 UI·이력 저장 / 관리자 백오피스 / 부적절 콘텐츠 필터 / 파일 업로드 검증·CSRF·레이트리밋 / 오류·예외 화면 / 비용 상한 |
| **E1 병행** | 테스트 전략(크레딧 트랜잭션·골든 이미지·API 목킹) / CI·배포·롤백 절차 |
| **E6** | 퍼널 이벤트 수집 / 크레딧 소비 분포 집계 / 모니터링·알림 구체화 |
| **Phase 6** | 결제 실패·대사 처리 / 환불 정책 / 세금계산서 / 통신판매업 신고·사업자정보 표시 |

**E1이 크게 늘어난다.** 그러나 여기 있는 것들은 "나중에 붙이는 기능"이 아니라 **없으면 서비스를 열 수 없는 것들**이다. 특히 관리자 백오피스는 베타 운영 방식 자체가 전제하고 있으므로 미루면 베타를 시작할 수 없다.
