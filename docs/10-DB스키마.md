# DB 스키마 (Stage 10)

> PostgreSQL 기준. Stage 2의 엔티티를 실제 테이블로 옮긴다.

## 설계 판단 — 정규화와 JSONB의 경계

공연정보에는 회차·출연진·가격처럼 배열 필드가 많다. 이를 모두 별도 테이블로 쪼개면 테이블이 열 개 넘게 늘어나고, 프로젝트 하나를 읽을 때마다 조인이 쌓인다. 반대로 전부 JSONB에 넣으면 목록 화면에서 공연명·날짜로 정렬할 수 없다.

**기준을 이렇게 나눈다.**

| 대상 | 저장 방식 | 근거 |
|---|---|---|
| 프로젝트 간 조회·정렬·필터에 쓰이는 값 | **컬럼** | 홈 대시보드 목록, 검색 |
| 항상 프로젝트 단위로 통째 읽고 쓰는 값 | **JSONB** | 회차·출연진·가격·주최 등. 프로젝트를 넘나드는 검색이 없다 |
| 프로젝트를 가로질러 집계·분석하는 값 | **정규화 테이블** | SelectionEvent, LayoutSample. 통계가 목적이므로 컬럼이어야 한다 |

공연정보를 JSONB로 두는 대신, 목록에 필요한 `main_title`·`genre`·`primary_date`는 컬럼으로 중복 저장한다. 저장 시 애플리케이션이 함께 갱신한다.

## 3. 규격 — 테이블 없음

기본 규격 13종은 애플리케이션 상수(enum)로 두고 테이블을 만들지 않는다. 근거는 Stage 2 "규격 정의 — 테이블이 아니라 상수" 참조.

커스텀 규격도 별도 레코드를 만들지 않고, 결과물이 `format_code='CUSTOM'`과 실제 `width`·`height`를 직접 들고 있는다. 한 번 쓰고 마는 치수가 참조 없는 행으로 쌓이는 것을 막는다.

## 6-2. credit_transactions (크레딧 이력)

잔액만 두면 "왜 이만큼 남았는지" 설명할 수 없다. 모든 증감을 이력으로 남기고 `accounts.credit_balance`는 그 합계의 캐시로 취급한다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | bigserial | PK | |
| account_id | uuid | FK→accounts, NOT NULL | |
| type | text | CHECK (signup_grant/purchase/consume/refund/admin_grant) | |
| amount | integer | NOT NULL, CHECK (<> 0) | 증가는 양수, 소비는 음수 |
| balance_after | integer | NOT NULL | 기록 시점 잔액 — 사후 검증용 |
| job_id | uuid | FK→jobs, null 허용 | 소비·환불의 원인 작업 |
| actor_id | uuid | FK→accounts, null 허용 | **관리자 지급 시 조작한 관리자.** 감사 추적용 |
| description | text | | "규격 일괄변환 3종", "베타 지급" 등 |
| created_at | timestamptz | default now() | |

```sql
CREATE INDEX idx_credit_account ON credit_transactions (account_id, created_at DESC);
-- 작업당 소비는 1건만 (재시도로 중복 차감되는 사고 방지)
CREATE UNIQUE INDEX uq_credit_consume_job ON credit_transactions (job_id)
  WHERE type = 'consume';
```

**차감 시점은 작업 등록 시다.** 생성이 끝난 뒤 차감하면 무료로 생성할 여지가 생기고, 잔액 확인만 하고 차감을 미루면 동시 요청에서 잔액이 음수가 된다. 잔액 갱신과 이력 기록, 작업 등록을 **한 트랜잭션**으로 묶고, `credit_balance`에 `CHECK (>= 0)`을 걸어 DB가 마지막 방어선이 되게 한다.

작업이 실패하면 `refund`로 되돌린다. 부분 실패(일괄변환 중 일부 규격)는 실패한 하위 작업 몫만 환불한다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK | |
| project_id | uuid | FK→projects | |
| kind | text | CHECK (draft_generate / decompose_layers / recompose / resync / render_print / zip_download / analyze_poster) | |
| status | text | CHECK (pending/running/succeeded/failed/canceled) | |
| payload | jsonb | | 대상 규격 목록 등 |
| result | jsonb | | 생성된 asset id 목록 |
| error | text | | 실패 사유 |
| attempts | smallint | default 0 | 재시도 횟수 |
| parent_job_id | uuid | FK→jobs, null 허용 | 일괄변환의 규격별 하위 작업 |
| locked_at | timestamptz | | 워커 점유 시각 |
| created_at / updated_at | timestamptz | | |

```sql
CREATE INDEX idx_jobs_queue ON jobs (created_at)
  WHERE status = 'pending';
```

**워커의 작업 획득**은 경합을 피하기 위해 다음 방식을 쓴다.

```sql
UPDATE jobs SET status='running', locked_at=now()
WHERE id = (
  SELECT id FROM jobs WHERE status='pending'
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED LIMIT 1
) RETURNING *;
```

`FOR UPDATE SKIP LOCKED`를 쓰면 워커를 여러 대로 늘려도 같은 작업을 중복 처리하지 않는다. `locked_at`이 오래된 running 작업은 죽은 워커의 것으로 보고 pending으로 되돌린다.

**일괄변환의 부분 실패**: 규격별로 하위 job을 만들고 `parent_job_id`로 묶는다. 부모의 상태는 자식 전체가 끝났을 때 결정하며, 일부 실패해도 성공분은 그대로 남는다.

## 권한 처리

Spring Boot 서버 렌더링 구조에서는 모든 DB 접근이 애플리케이션을 거치므로, 권한 판단은 **서비스 계층**에서 한다.

- 조회는 항상 `owner_id = 현재 사용자` 조건을 포함한다. 조건 없이 id만으로 조회하는 리포지토리 메서드를 만들지 않는다
- 소유자가 아닌 접근은 존재를 숨기기 위해 `404`로 응답한다
- `generated_assets`·`uploaded_files`·`print_order_drafts`는 소속 프로젝트를 조인해 소유자를 확인한다

PostgreSQL Row Level Security는 필수가 아니지만, 정리 배치나 분석 스크립트가 DB에 직접 접속할 때를 대비한 이중 방어로 검토할 수 있다. 이 경우 애플리케이션 접속 계정과 배치용 계정을 분리한다.

## 회원 탈퇴 처리

탈퇴 시 개인 데이터는 전부 삭제한다. 다만 **전부 지우면 안 되는 것과 지울 수 없는 것**이 각각 있어 세 갈래로 나눈다.

### ① 삭제 — 개인 데이터

`accounts`, `projects`, `performance_info`, `uploaded_files`, `generated_assets`, `print_order_drafts`와 스토리지의 모든 파일(원본·미리보기 포함)을 삭제한다. 프로젝트는 고객의 자산이므로 탈퇴 의사를 밝힌 이상 남길 이유가 없다.

### ② 익명화 — 선택 로그와 학습 데이터

`selection_events`와 `layout_samples`는 **삭제하지 않고 소유자 정보만 끊는다**(`owner_id`, `project_id`를 null로).

이 데이터에는 개인을 식별할 정보가 들어 있지 않다. "어떤 후보들 중 무엇을 골랐는가"의 기록일 뿐이다. 그런데 이것이 ACTSET의 핵심 자산이므로, 탈퇴할 때마다 통째로 지우면 **누적된 학습 근거가 계속 깎여 나간다.** 스키마의 FK를 `ON DELETE SET NULL`로 둔 것이 이 처리를 위해서다.

식별자를 끊어 개인을 특정할 수 없게 만든 정보는 개인정보로 보지 않는다는 것이 일반적 해석이나, **최종 판단은 법률 자문으로 확인해야 한다.** 개인정보처리방침에도 이 내용을 명시해야 한다.

### ③ 보존 — 결제 기록 (Phase 6부터)

크레딧 **충전**은 결제이므로 전자상거래법상 대금 결제 기록 보존 의무가 발생한다. 탈퇴하더라도 `credit_transactions` 중 `type='purchase'` 건은 법정 기간 동안 보존해야 하며, 이는 선택 사항이 아니다. 이때도 이름·연락처는 지우고 결제 식별자와 금액만 남기는 형태로 최소화한다.

베타 기간에는 결제가 없으므로 해당 사항이 없다. 다만 **결제를 붙이는 시점에 탈퇴 로직을 함께 손봐야 한다**는 점을 잊지 않도록 여기에 적어 둔다.

### 처리 방식

- 탈퇴 요청 즉시 계정을 비활성화하고 로그인을 차단한다
- 실제 삭제는 배치로 처리한다. 파일이 많으면 즉시 삭제가 오래 걸려 요청이 지연된다
- 실수 탈퇴에 대비한 유예기간(예: 7일)을 둘지는 정책 판단이며, 두는 경우 "유예 중에는 로그인만 하면 복구"로 안내한다

## 정리 배치 (일 1회)

| 대상 | 조건 | 처리 |
|---|---|---|
| 삭제된 결과물 | `deleted_at < now() - 30일` | 레코드·파일(미리보기 포함) 하드 삭제 |
| 미확정 draft | `status='draft' AND created_at < now() - 30일` | 프로젝트·하위 데이터 삭제 |
| 삭제된 프로젝트 | `status='deleted' AND deleted_at < now() - 30일` | 프로젝트·결과물·파일 하드 삭제 |
| 탈퇴 계정 | `status='withdrawn' AND deleted_at < now() - 유예기간` | 개인 데이터 삭제, 선택로그 익명화 |
| 미선택 시안후보 | 프로젝트 확정 후 30일 경과 | 이미지 파일만 삭제(레코드는 유지) |
| 만료 대용량 파일 | `download_expires_at < now()` | **원본 파일만** 삭제하고 `image_url=null`. 레코드와 `preview_image_url`은 남긴다 |
| 죽은 작업 | `status='running' AND locked_at < now() - 30분` | pending으로 복구 |

## 마이그레이션 순서

`accounts → projects → generated_assets → uploaded_files → jobs → credit_transactions → selection_events → print_order_drafts → layout_samples` 순으로 만든다. FK 의존 방향과 일치한다.

`credit_transactions.job_id`가 `jobs`를 참조하므로 **`jobs`가 `credit_transactions`보다 먼저** 생성되어야 한다.
