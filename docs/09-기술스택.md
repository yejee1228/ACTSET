## Python 재검토 — 왜 필요 없는가

초판에서 Python을 권한 근거는 "OCR·VLM·세그멘테이션 생태계가 Python"이라는 것이었다. 이 근거는 두 지점에서 틀렸다.

### 1. AI 모델은 어떤 언어를 쓰든 우리 코드 밖에서 돈다

Qwen2.5-VL, SAM2, PaddleOCR, Qwen-Image-Layered는 모두 **GPU가 필요한 모델**이다. 2인 팀이 이를 애플리케이션 프로세스 안에서 직접 구동하는 선택지는 처음부터 없었다. 서버리스 GPU(Replicate·Modal 등)나 별도 추론 서버에 올려 **HTTP로 호출**하게 된다.

즉 이 모델들은 Python 라이브러리가 아니라 **HTTP 엔드포인트**로 존재한다. Java에서 호출하는 데 아무 문제가 없다. Python을 쓴다고 해서 모델이 더 가까워지지 않는다.

### 2. 텍스트 레이어 렌더링은 Java2D가 동등하게 처리한다 — 실측 완료

Python을 코드베이스에 넣어야 할 유일한 실질적 이유는 렌더링 엔진이었다. 이를 확인하기 위해 PoC 렌더러를 **Java2D로 이식해 같은 포스터를 렌더링**하였다(`poc-java/PosterRenderer.java`).

| 항목 | Python (Pillow) | Java (Java2D) |
|---|---|---|
| 한글 렌더링 | 정상 | **정상** (Noto Sans CJK KR을 TTC에서 직접 로드) |
| 텍스트 레이어 합성 시간 | 86ms | **82ms** |
| A3 300dpi 텍스트 선명도 | 양호 | **양호** |
| 결과물 차이 | — | 육안으로 구분되지 않음 |

Java2D는 오히려 타이포그래피 제어가 세밀하다. `TextLayout`과 `AttributedString`으로 커닝·자간·합자를 다루고, `FRACTIONALMETRICS`로 소수점 단위 자간을 유지한다. 인쇄용 PDF는 **Apache PDFBox**가 CMYK·재단여백·폰트 임베딩을 모두 지원해 Python 쪽 대안보다 낫다.

### 3. Python이 여전히 나은 영역과 그 처리

| 영역 | 판단 |
|---|---|
| 학습 데이터 집계(LayoutSample 분포 분석) | pandas·numpy가 편하다. 다만 이는 **상시 서비스가 아니라 가끔 돌리는 배치 분석**이다. 노트북이나 단독 스크립트로 두고 운영 코드에 넣지 않는다. 상당 부분은 PostgreSQL 집계 쿼리로도 처리된다 |
| 모델 파인튜닝 | 현재 범위 밖. 자체 모델을 만들지 않는 것이 전략이다(Stage 5) |

**결론: 운영 코드베이스는 Java 하나로 간다.** 분석용 Python 스크립트가 별도로 존재하는 것은 무방하며, 이는 언어가 둘이라는 부담과 성격이 다르다.

## 권장 구성

| 영역 | 선택 | 이유 |

| 작업 큐 | **DB 기반 jobs 테이블** + `@Scheduled` 폴링 | 별도 미들웨어 없이 시작 |

| AI 타이포그래피 | **Qwen-Image-3.0** (선택) | 타이틀 모드 B. 한국어 포함 12개 언어 지원 |
| LLM | **GPT-5.6** | 공연정보 구조화 보조·카피 생성. MVP에서는 역할이 작다(Stage 14) |
| 메일 발송 | **AWS SES 등** (미선정) | 비밀번호 재설정·알림의 전제 (Stage 15) |
| AI 호출 | **HTTP 클라이언트** (`RestClient`) | 이미지 생성 API, 서버리스 GPU |
| 배포 | **컨테이너** (Fly.io · Render · AWS) | Spring Boot 단일 jar |

### 초판 대비 가장 큰 이점 — 배포 단위가 하나

초판은 웹(Next.js/Vercel)과 워커(Python/Fly.io)를 따로 배포하는 구조였다. 개정안은 **같은 코드베이스, 같은 jar**를 프로필로 나눠 실행한다.

```
web 프로필    : HTTP 요청 처리 (화면·API)
worker 프로필 : jobs 테이블 폴링 → 렌더링·AI 호출
```

도메인 모델과 렌더링 코드를 양쪽이 그대로 공유하므로, 언어 경계에서 생기던 직렬화·중복 정의가 사라진다. 2인 팀에서 이 차이는 크다.

## 화면 기술 — React + TypeScript (확정)

최근 사용 경험이 있는 React로 확정하였다. TypeScript를 함께 쓴다.

React가 적합한 이유는 다음 화면들이 실제로 클라이언트 상태를 요구하기 때문이다.

| 화면 | 필요한 상태 |
|---|---|
| ⑥ 편집 모드 | object_map 요소의 드래그·리사이즈 — 서버 왕복 없이 즉시 반응해야 한다 |
| ③·⑥ 후보 선택 | 여러 후보를 비교하며 고르는 동안의 임시 선택 상태 |
| 작업 진행 | 여러 규격의 하위 작업 진행률을 동시에 추적 |
| ② 추가정보 | 9개 그룹의 입력 상태와 자동저장 디바운스 |

**빌드 도구는 Vite**를 쓴다. Next.js는 SSR·라우팅·API 라우트를 제공하지만, 이 서비스는 로그인 뒤에 쓰는 도구라 SEO가 필요 없고 API는 Spring Boot가 담당한다. Next.js를 쓰면 겹치는 층이 생긴다. 소개 페이지(0-A)만 SEO가 의미 있는데, 이는 정적 페이지로 충분하다.

**상태 관리**는 서버 상태와 화면 상태를 나눈다. 서버 데이터는 TanStack Query로 캐시·폴링·재검증을 맡기고(작업 진행 폴링이 특히 간단해진다), 편집 모드 같은 순수 화면 상태만 로컬에 둔다.

### 배포 구성

프런트엔드는 정적 빌드 산출물이므로 다음 두 방식이 모두 가능하다.

| 방식 | 설명 |
|---|---|
| **Spring Boot에 내장** (권장) | 빌드 결과를 `static/`에 넣어 단일 배포. CORS·쿠키 도메인 문제가 없다 |
| 별도 호스팅 | CDN 배포. 배포는 빨라지지만 CORS·인증 쿠키 설정이 늘어난다 |

초기에는 내장을 권한다. 배포 단위가 하나로 유지되고, 세션 쿠키가 같은 도메인에서 동작해 인증이 단순해진다.

## 이미지 생성 — Ideogram 4.0

Ideogram 4.0은 이미지 **한 장 단위 과금**이며 구독이 없다. 크레딧 단가를 원가와 직접 연동하기에 적합하다.

| 티어 | 장당 단가 | 용도 |
|---|---|---|
| Turbo | $0.03 | 빠른 미리보기 — 현재 계획에는 없음 |
| **Default** | **$0.06** | 시안 후보 생성의 기본값 |
| **Quality** | **$0.10** | 최종 확정본·인쇄용 |

**시안 3안 생성 시 원가**는 Default 기준 $0.18(약 250원), Quality 기준 $0.30(약 420원)이다. 이 값이 Stage 6 크레딧 단가 산정의 출발점이 된다.

**티어를 나눠 쓰는 전략**을 권한다. ③에서 후보를 고르는 단계는 Default로 뽑고, 사용자가 고른 안만 Quality로 다시 생성한다. 버려질 후보에 비싼 단가를 쓰지 않으므로 원가가 크게 줄어든다. 다만 Default와 Quality의 결과가 눈에 띄게 달라지면 "고른 것과 다른 게 나왔다"는 불만이 생기므로, **PoC에서 두 티어의 차이를 먼저 확인**하고 결정한다.

### 한글 지원은 더 이상 문제가 아니다

Ideogram 4.0은 공식 문서에 한국어 지원이 명시되어 있지 않고, 한글 렌더링이 부족하다는 사용자 보고도 있다. **그러나 모든 텍스트를 별도 레이어로 얹기로 확정했으므로(Stage 5) 이 모델에게 글자를 맡기지 않는다.** 오히려 배경에 글자가 들어가지 않도록 네거티브 프롬프트로 억제하는 것이 과제다.

### AI 타이포그래피 — Qwen-Image-3.0 (선택 기능)

타이틀을 폰트 대신 AI로 생성하는 모드 B에 쓴다. **한국어를 포함한 12개 언어의 텍스트 렌더링을 지원**한다고 명시되어 있다.

주의점이 두 가지 있다. **문자열을 따옴표로 정확히 감싸야** 하며, 설명형으로 쓰면 모델이 문구를 임의로 바꾼다. 그리고 **프롬프트 자동 확장 기능을 반드시 꺼야 한다.** 켜져 있으면 문구가 재작성된다. 두 규칙 모두 공연명을 다루는 이 서비스에서는 치명적이므로 연동 코드에서 강제한다.

## 서버리스 GPU vs 자체 추론 서버

Qwen2.5-VL·SAM2·PaddleOCR 같은 오픈소스 모델은 **파일(가중치)일 뿐이고, 실행하려면 GPU가 달린 컴퓨터가 필요하다.** 그 GPU를 어떻게 마련할지의 선택지다.

| | 자체 추론 서버 | 서버리스 GPU (Replicate·Modal 등) |
|---|---|---|
| 방식 | GPU 서버를 빌려 24시간 켜두고 모델을 올려둔다 | 호출할 때만 GPU가 켜지고 초 단위로 과금 |
| 비용 | 안 써도 매달 고정 지출 | 안 쓰면 0원 |
| 응답 속도 | 항상 대기 상태라 즉시 응답 | 첫 호출 시 모델 로딩 대기(콜드스타트) 수초~수십초 |
| 운영 부담 | GPU 드라이버·모델 배포·장애 대응을 직접 | 벤더가 처리 |

**ACTSET에는 서버리스가 맞다.** 이 모델들이 필요한 곳은 두 군데뿐이다.

1. **학습 파이프라인** — 포스터 100건을 분석하는 배치 작업. 가끔 한 번 돌린다
2. **고객의 기존 포스터 업로드 분석** — Phase 3 이후 기능이며 MVP 범위 밖

둘 다 **상시 가동이 필요 없다.** 자체 서버를 두면 하루 대부분 놀고 있는 GPU에 매달 돈을 내게 된다. 콜드스타트 지연도 배치 작업에서는 문제가 되지 않는다.

호출량이 늘어 서버리스 누적 비용이 상시 서버 비용을 넘어서는 시점에 전환을 검토하면 된다. 그 전에 미리 옮길 이유는 없다.

## 비동기 생성 처리

```
① 사용자가 "일괄변환 생성" 클릭
② 웹: jobs 테이블에 작업 등록(pending) → job_id 즉시 응답
③ 워커(@Scheduled): FOR UPDATE SKIP LOCKED로 작업 획득
④ 저장된 레이어 스택 로드 (분해는 확정 시 1회만 수행됨)
⑤ 배경판 확장·피사체 재배치 → Java2D로 사진(PHOTO)·텍스트 레이어 렌더링·합성 → S3 업로드
⑥ generated_assets 기록, jobs.status=succeeded
⑦ 화면: TanStack Query 폴링으로 완료 감지
```

**부분 실패 처리**: 일괄변환은 규격별 하위 작업으로 나눈다. 규격 하나가 실패해도 나머지는 살리고, 실패분만 재시도한다.

## 파일 저장 구조

```
projects/{project_id}/
  base/{asset_id}.png        # 생성 비주얼 원본 — 정보 변경 시 재사용
  layers/{layer_id}.png      # 분해된 RGBA 레이어(배경판·피사체·장식) — 모든 규격이 공유
  render/{asset_id}.jpg      # 합성 결과 — 정보 변경 시 교체
  preview/{asset_id}.jpg     # UI 표시용 축소본 — 영구 보관
  print/{asset_id}.pdf       # 인쇄용 (Phase 6)
  uploads/{file_id}.{ext}    # 공연사진·로고·참고이미지
```

`layers/`가 핵심이다. 시안 확정 시 1회 분해해 저장하면, 이후 모든 규격 변환이 이 레이어를 재배치하는 것으로 끝난다. 정보만 바뀌면 `render/`만 교체하므로 생성 API를 호출하지 않는다.

## 보안·권한

- **Spring Security** 세션 인증. 모든 DB 접근이 애플리케이션을 거치므로 권한 판단은 서비스 계층에서 한다
- 타인의 프로젝트 조회는 존재를 숨기기 위해 `404`로 응답한다
- PostgreSQL Row Level Security는 필수가 아니다. 초판은 클라이언트가 DB에 직접 접근하는 구조를 전제했으나, 현재 구조에서는 Spring Boot가 유일한 통로다. 다만 **정리 배치나 분석 스크립트가 직접 접속할 때를 대비한 이중 방어**로 걸어두는 것은 검토할 만하다
- 결과물은 공개 URL이 아니라 만료되는 서명 URL로 제공한다

## 한글 폰트

텍스트 레이어를 서버에서 렌더링하고 그 결과가 **인쇄물로도 나가므로**, 라이선스에서 확인할 항목이 일반 웹폰트보다 많다.

| 확인 항목 | 왜 필요한가 |
|---|---|
| 서버 사이드 이미지 렌더링 | 웹폰트 임베딩과 별개 조항인 경우가 있다 |
| 인쇄물 사용 | 포스터·현수막으로 출력된다 |
| 상업적 이용 | 유료 서비스의 결과물이다 |
| 재배포 금지 조항 | 서버에만 두고 사용자에게 폰트 파일 자체를 내려주지 않으면 대개 문제없다 |

**구입 전에 무료 폰트를 먼저 검토하기를 권한다.** 국내에는 상업적 이용이 가능한 고품질 한글 폰트가 여럿 있으며, 대표적으로 **Pretendard**(SIL Open Font License)와 **본고딕/Noto Sans KR**(SIL OFL)이 있다. SIL OFL은 상업적 사용·수정·임베딩을 허용하고 폰트 파일 자체를 유료로 판매하는 것만 금지하므로, 이 서비스의 사용 형태와 충돌하지 않는다. PoC 렌더링도 Noto Sans CJK KR로 수행했고 결과 품질에 문제가 없었다.

유료 폰트가 필요한 경우는 **브랜드 아이덴티티상 특정 서체가 필요할 때**이지, 기능상 필수는 아니다. 다만 라이선스 해석은 최종적으로 각 폰트의 약관을 직접 확인해야 한다.

## 확정하지 않은 것

1. **Ideogram Default / Quality 티어 운용** — 후보는 Default, 확정본은 Quality로 나눌지 PoC에서 두 결과를 비교한 뒤 결정
2. **AI 타이포그래피(모드 B) 채택 여부** — PoC Q7. 실패해도 기본 모드가 있어 서비스에는 지장 없음
3. **폰트 확정** — 무료(Pretendard·Noto) 검토 후 필요 시 구입
4. **레이어 분해 품질** — PoC Q6 결과에 따라 규격 변환 전략이 달라진다. 실패 시 SAM2 절충안 또는 규격별 배경 별도 생성으로 후퇴
5. **AWS 리전·인스턴스 규모** — RDS와 S3 리전을 서울(ap-northeast-2)로 맞춰 전송 지연·비용을 줄인다
